# KOSIS 통계표 구조 변경 대응 절차 (v1.17.0)

KOSIS 는 통계표의 분류 단계·항목 구성을 예고 없이 바꾸기도 한다. 2026-10 에는 등록장애인 통계 3종
(`DT_11761_N007`·`N008`·`N010`)과 장애인 사회참여 통계(`DT_438001_AC016`)에서 예전 "항목"이던
성별·사회참여 활동이 "분류"로 옮겨 가, 기존 조회 주소가 `err=20`(필수 요청변수 누락)을 돌려받았다.
이 문서는 같은 일이 다시 생겼을 때 코드를 고치지 않고 **설정만 바꿔** 복구하는 절차다.

## 1. 알아차리는 경로

| 경로 | 무엇이 보이나 |
|---|---|
| 알림 메일 | 정기 실행이 실패하면 "[IITP 데이터 수집] … 이상" 메일. 실패 통계·사유·권장 조치가 담긴다 |
| 운영 콘솔 [운영] › 데이터 수집 | 작업별 마지막 정기 실행·연속 실패·실패 목록 |
| 서버 로그 | `logs/run_summary.log` 한 줄 요약, `logs/<날짜>.log` 상세 |

실패한 통계는 **적재 전 단계에서 멈추므로 기존 데이터가 그대로 남는다.** 서두를 필요는 없다.

## 2. 사유별 원인

| 사유 문구 | 뜻 |
|---|---|
| `err=20(필수 요청변수 누락 — 통계표 구조(분류 단계) 변경 의심 …)` | 분류 단계가 늘어 조회 주소의 `objL` 이 모자란다 |
| `err=21(요청변수 값 오류 …)` | 조회 주소에 적은 분류·항목 코드가 원천에서 바뀌었다 |
| `구조 변경 감지 — 응답의 C4(성별) 분류가 통합 테이블 칸에 배치되지 않음` | 응답은 받았지만 분류 단계가 칸 배치 규칙보다 많다 |
| `구조 변경 감지 — 항목이 N개` | 분류를 itm_id 로 옮기는 규칙인데 항목이 2개 이상이 됐다 |
| `같은 연도 기존 행의 N%만 이번 응답과 키가 일치` | 분류 체계·코드가 바뀌었거나 칸 배치 규칙이 어긋났다 |
| `기존 연도 YYYY 가 이번 응답에 없음` | 원천 제공 기간이 줄었거나 응답 일부가 빠졌다 |
| `메타에 이름이 없는 분류/항목 코드 N건` | 데이터 코드가 메타에 없다. 그대로 적재하면 공개 API 조회가 오류로 끝난다 |

## 3. 현재 구조 확인

KOSIS 메타 API 로 통계표의 객체 구성을 본다(인증키는 `sys_ext_api_info.auth`).

```
https://kosis.kr/openapi/statisticsData.do?method=getMeta&type=ITM&format=json&jsonVD=Y
    &apiKey=<인증키>&orgId=<기관>&tblId=<통계표ID>
```

응답의 `OBJ_ID`·`OBJ_NM` 별로 묶으면 `ITEM`(항목)과 분류 객체들이 나온다. 분류 객체의 **나열 순서가
`objL1`, `objL2`, … 순서**다. 예) N007 = `ITEM`(T001 인원) / `YRE` 연령 / `GRA` 장애정도 / `D` 성별.

## 4. 설정 고치기 (`sys_stats_src_api_info`)

### 4-1. 조회 주소 `api_data_url`

분류 단계 수만큼 `objL1`~`objLn` 을 채운다(`ALL` 또는 코드 목록). `itmId` 는 현재 항목 코드로 바꾼다.

### 4-2. 칸 배치 규칙 `intg_col_map`

통합 테이블(`stats_dis_*`)과 소비처(공개 API·대시보드)는 칸이 `c1`·`c2`·`c3`·`itm_id` 넷뿐이고,
예전 형태를 전제로 한다. 늘어난 분류를 예전 자리로 되돌리는 규칙을 적는다.

| 키 | 값 |
|---|---|
| `c1`·`c2`·`c3`·`itm_id` | 원본 칼럼 `"C1"`~`"C4"`·`"ITM"` 또는 `null`(빈 값). 적지 않은 키는 종전 규칙(c1←C1, c2←C2, c3←C3, itm_id←ITM) |
| `item_obj` | 메타에서 "항목"으로 다룰 분류 객체 ID. `itm_id` 를 분류에서 가져오면 반드시 적는다 |

2026-10 적용 값:

| 통계표 | 규칙 |
|---|---|
| `DT_11761_N007` | `{"c3": null, "itm_id": "C3", "item_obj": "D"}` |
| `DT_11761_N010`·`DT_11761_N008` | `{"itm_id": "C4", "item_obj": "D"}` |
| `DT_438001_AC016` | `{"c2": null, "c3": null, "itm_id": "C2", "item_obj": "B"}` |

쓰지 않는 칸은 `null` 로 **명시**한다. 그래야 원천이 분류를 또 늘렸을 때 "구조 변경 감지"로 바로 드러난다.

## 5. 시험 → 적재

1. **파일 저장만** 실행해 원천 응답을 받아 본다(DB 는 바뀌지 않는다).
   대상 통계만 돌리려면 `.env` 의 `DATA_COLLECTION_SCOPE=PARTIAL` 과 대상 목록을 쓴다.
   ```
   python main.py --mode file
   ```
   저장된 `kosis_data/<날짜>/data/*.json` 에서 분류 칼럼(C1~C4)·항목(ITM_ID)이 규칙과 맞는지 본다.
2. **적재** 실행.
   ```
   python main.py --mode db
   ```
   적재 직전에 다음을 자동으로 확인하고, 하나라도 어긋나면 그 통계만 되돌린다(기존 데이터 유지).
   - 응답 구조가 칸 배치 규칙과 맞는가
   - 기존 연도가 모두 있고, 같은 연도 기존 행의 절반 이상이 키(시점·분류·항목)가 일치하는가
   - 데이터의 모든 코드가 메타에 이름으로 있는가
3. 원천의 분류 체계가 **실제로 바뀌어** 기존 데이터와 키가 맞지 않는 것이 정상인 경우에만,
   확인 후 해당 통계에 한 번 허용한다. `.env` 나 cron 에는 넣지 않는다.
   ```
   KOSIS_ACCEPT_RESHAPE=DT_xxxx python main.py --mode db
   ```

일부 통계만 실행(PARTIAL)·파일 저장만 실행한 결과는 실행 기록에만 남고 알림 메일은 보내지 않는다.
외부 시스템 전체 동기화 시각(`sys_ext_api_info.latest_sync_time`)도 전체 실행에서만 갱신된다.

## 6. 수집 기간

연도 주기(`prdSe=Y`·`F`) 통계는 수집 종료연도를 **올해까지** 넓혀 요청한다. KOSIS 는 아직 공표되지
않은 연도를 범위에 섞어 요청해도 있는 연도만 돌려준다. 적재에 성공하면 `stats_src_data_info.collect_end_dt`
가 실제로 받은 마지막 연도로 앞당겨진다(줄이지는 않는다). 월·분기 주기는 등록된 기간을 그대로 쓴다.

## 7. 알림 메일 설정

- 수신 주소·사용 여부: 운영 콘솔 [운영] › 데이터 수집 › 이상 발생 시 알림 메일 (`sys_ops_setting`)
- 발신 방식: 수집 서버 `.env` 의 `MAIL_*`·`GRAPH_*`·`SMTP_*` (`.env.example` 참고)
- 발송 시험: `python scripts/send_test_alert.py` — 현재 설정으로 시험 메일 1통을 보낸다
